# Backup and recovery

Tidal owns one SQLite database, one configuration, one encrypted signing key and
one runtime release. Recovery restores that state, checks retained transactions,
refreshes current observations and waits for explicit activation. The backup
playbook retrieves saved inputs and invokes the app-owned installation and recovery
commands. Tidal owns service holds, state preparation and worker resumption.

## What to retain

- A verified `tidal db snapshot`, including its schema and database identity.
- The exact release archive: Python/SQLite runtime, pinned dependency wheels,
  application source, installation helper and built UI.
- The effective `config/server.yaml`, selected secret file, original encrypted
  keystore, service definitions and their checksums. Keep the secret file and
  keystore recoverable even if the original host is lost.
- The repository credentials and encryption password outside the failed host.

The local activation file is **excluded**. It grants this instance permission to
execute and must be regenerated by `tidal resume`. Do not separately copy a live
SQLite database, WAL and SHM file as though they were a consistent snapshot.

Create an online snapshot without loading credentials or contacting services:

```bash
tidal db snapshot --database /path/to/tidal.db --output /backup/new-snapshot.sqlite3 --json
```

Existing output files are never overwritten. The snapshot is checked before
publication and carries a checksum. The outer backup job copies it and its
matching runtime/configuration to the existing backup destination. The deployed
backup scheduler determines cadence. Electro uses its existing Storage Box.

## Restore, then resume

For Electro's existing `tidal-capture-v1` archives, use the app-owned installer
from a reviewed Tidal checkout. It supports the retained offline runtime inside
the capture, including releases created before this restore command existed.
The replacement needs the same service user and paths as the original host.

1. Isolate the original signing instance, retrieve the selected capture from
   storage, verify its recorded checksum and restore while held:

   ```bash
   sudo python3 scripts/deploy_release.py restore --capture /private/capture.tar.gz --sha256 CAPTURE_SHA256
   ```

   This verifies every member, prepares the exact saved runtime offline, restores
   the consistent database and configuration, and starts only the read-only API.
   It never upgrades the saved schema. Native preparation rotates API access,
   marks prices stale and suppresses old alerts while preserving transaction
   identities, amounts, timestamps and history. The fresh API credential is in
   `/home/wavey/.tidal/recovery-access.json`, readable only by its owner.

   Existing database files or sidecars require explicit `--overwrite`; displaced
   state is retained privately. Retry the identical command after interruption.
   The receipt prevents recopying the database after native preparation, and
   workers remain held across reboot. Preserve the receipt and retained inputs.

2. Check API health, actual restored dashboard/log data, authentication and public
   routing. The API can serve saved data while RPC is unavailable. After confirming
   source isolation and resolving any ambiguous external actions, explicitly resume:

   ```bash
   sudo python3 scripts/deploy_release.py resume
   ```

   The installer verifies the retrieved capture matches the active release and
   database, reconciles known transactions, refreshes observations without sending
   transactions or notifications, and invokes native activation. It then starts
   normal worker cycles and enables the existing timers. A failed worker cycle
   reinstates the hold. Known pending transactions continue to block their signer.

Verify a normal cycle or legitimate no-work result, independently retrieve a
post-recovery backup and the next scheduled backup, and record elapsed recovery
time and necessary manual decisions. These live checks remain commissioning
work; local command tests do not prove replacement-host recovery.

For diagnosis, the existing `tidal check-config`, `tidal db check`, `tidal status`,
`tidal reconcile` and `tidal refresh --recovery` commands remain available. Native
`tidal resume` alone does not enable systemd timers; use the installer above for
Electro's complete resumption procedure.

## Pending transactions and historical gaps

An included transaction remains provisional until canonical finalized evidence
matches its exact signer, nonce, hash and unsigned intent. Missing events or
conflicting evidence require review. An unavailable receipt is not proof that a
transaction was never broadcast.

To prove that an external replacement consumed an original nonce:

```bash
tidal reconcile --transaction-id 123 --replacement-hash 0xREPLACEMENT --note 'Reviewed external nonce resolution' --json
```

This records the original attempt as superseded; it does not manufacture a
successful kick or settlement. There is no automatic retry or replacement.

Review a specific old auction/token history before applying a baseline:

```bash
tidal db repair-auction-rounds --auction 0xAUCTION --token 0xTOKEN --json
tidal db repair-auction-rounds --auction 0xAUCTION --token 0xTOKEN --apply --json
```

The preview lists proposed baseline IDs. Applying a baseline refuses unresolved
attempts and does not change unrelated pairs. Missing old history remains
explicit; a baseline is an operator policy decision, not reconstructed evidence.

## One-time legacy transition

Before the first consolidation upgrade, fence all old writers and preserve a
coherent original main database and operator outbox. Migrate a separate working
database using those protected originals:

```bash
tidal db migrate --config /path/to/server.yaml --source-database /protected/original.db --outbox /protected/original-outbox.db --json
```

Migration imports retained submissions before retiring action jobs and unsigned
previews. It preserves all business rows and exact historical values. Repeating
the same interrupted migration is supported. Keep the originals after cutover;
they are evidence, not a second live database.

After any new attempt, rollback must preserve that attempt's identity and nonce.
Prefer forward repair. Restoring an earlier database after broadcasting can lose
the only record of a transaction that still exists on chain.


## API process configuration

The API uses the same configuration through an API settings loader that excludes
signing fields from every settings source. Its systemd unit removes inherited
keystore path/passphrase variables, and direct `api serve` refuses an environment
containing them. Worker configuration is unchanged. The API still runs under the
same operating-system account as the workers: this separates process configuration,
not filesystem authority. It is not a claim of isolation from a compromised API.
